# GPU march: progressive passes on Vulkan compute — design spec

Status: draft 2026-10-15, for owner review. Extends and amends `docs/spec.md`; on
landing, its sections fold into that spec and this file is deleted. Sequenced
after the nebula sections of `docs/spec.md`, so the field model it ports includes
those terms.

## Why

A final-quality cook of the stylized scene at face 512 reached 46% of its march
in two hours, heading for about 4.5 hours. A quick cook at face 256 takes about
1.5 minutes. Final quality fires 16 jittered rays per texel instead of 1, with
steps 2–5× shorter, so it costs 40–80× quick. Quick cooks are spotty for the same
reason: a single ray reports whether it happened to hit a sub-texel knot, so
those knots alias into isolated hot texels.

Two decisions need this fixed:
- **Look development.** Judging a sky in a 3D viewer needs final-quality cooks.
- **The resolution question.** It needs cooks at face 1024 and 2048.

At these costs, neither is practical.

`docs/spec.md` says "cook time is not a constraint", and lists a GPU
implementation as a non-goal. Both still hold for **correctness**: the CPU cook
stays the reference. They no longer hold for **turnaround**. This spec adds a GPU
path for speed and changes how both paths spend their rays, so that a cook
stopped early still leaves a usable sky.

Owner decisions (2026-10-15):
- **Vulkan compute, inside Starscape.** The repository stays standalone. It does
  not depend on Spehleon or the engine.
- **Every pass fires 1 ray per texel, always.** 16 jittered rays means 16 passes,
  accumulated, so stopping halfway leaves a half-resolved image.

## Scope

1. Progressive passes, for the CPU and GPU paths alike: pass order, accumulation,
   and writing the output after every pass.
2. A Vulkan compute march of the per-texel diffuse radiance and point budget.
3. One source for the field model, compiled both as C++ and as GLSL.
4. The device choice, fallbacks and build integration.

The calibration histogram, the star draws (Poisson counts and re-marching each
drawn star) and both previews stay on the CPU. They are small, branchy and
already fast.

Non-goals:
- Moving the calibration or the star draws to the GPU.
- More than 16 rays per texel.
- Jittering the step grid between passes.
- BC6H.
- Changing the file format. A partial file is an ordinary `.kre_starscape` (§1).
- Matching the CPU bit for bit (§3).

## 1. Progressive passes

### Order

A quality's S × S strata (S = `samplesPerAxis`, 4 for final, 1 for quick) are
visited one per pass, so a cook has S² passes. Within a pass, every texel fires
one ray, through the same stratum. The order keeps every prefix of passes evenly
spread over the texel. For S = 4, pass p with bits p₀ (lowest) to p₃ visits:

    quadrant  qx = p₀,      qy = p₀ ⊕ p₁
    sub-cell  sx = p₂,      sy = p₂ ⊕ p₃
    stratum   x  = 2qx + sx, y = 2qy + sy

So:
- pass 0 hits one corner and pass 1 the opposite one;
- passes 0–3 put one ray in each 2 × 2 quadrant;
- passes 0–7 put two diagonal rays in each quadrant;
- passes 0–15 hit every stratum once, which is today's 4 × 4 stratified jitter.

For S = 1 the single pass is the whole cook, which is quick quality.

### Jitter

Each ray's offset inside its stratum keeps today's draws. Today the cook fires stratum
k = S·y + x (row-major) from `RandomStream(seed, Jitter, texel, 0, 0)`. Each
sample takes two `NextDouble`s of two words each, which is one Philox block, so
stratum k's two uniforms come from block k. A pass computes that block directly, with no stream to replay:
`Philox4x32_10({texel, 0, Jitter << 24, k}, key)`. The words are taken in the
order `NextDouble` takes them. The GPU evaluates the same Philox in 32-bit
integer arithmetic, so CPU and GPU place every ray at the same jitter, up to the
float rounding of the final direction.

### Accumulation and output

- Per texel, the cook keeps a running sum of radiance (RGB) and of the point
  budget (24 bins). Each pass adds `weight · result` with weight 1/S² as today.
  After n passes the stored value is sum · S² / n, the mean of the rays fired so
  far.
- **After every pass**, the cook writes a complete output:
  1. scale the sums to the current mean;
  2. run the star-count bound checks (`kMaxStars`, `kMaxStarsPerTexelBin`) on
     that budget;
  3. draw the stars on the CPU from that budget, exactly as today: the Poisson
     streams are keyed by texel and bin, not by pass, so a texel's stars only
     change where its budget did;
  4. write `.kre_starscape` and the cubemap preview, if one was asked for,
     through today's temporary file and rename.

  Stopping the cook at any moment (Ctrl-C, a kill, a crash) leaves the last
  completed pass on disk. The cook needs no signal handling.
- A marched preview (`preview.march = true`) re-marches every pixel. It is written
  once, after the last pass.
- Progress reports `pass n/S²` with its own percentage and an ETA for the whole
  cook. When a cook ends, the final log line names the passes completed.

### What changes for existing cooks

The CPU sums a texel's 16 samples in pass order instead of row-major order, so
final-quality cooks change in their last bits. Quick cooks (S = 1) are unchanged.
The determinism contract still holds: the CPU output is byte-identical for any
thread count.

## 2. One source for the field model

The GPU march needs the whole field model:
- the noise;
- `EvaluateLocal`, for every galaxy component, the gas and the nebula terms;
- the population tables' per-step lookups;
- the step logic of `MarchRay` (transmittance, the straddle split, the budget).

Written twice, every model change, such as each nebula term, would have to be
made twice, and the two copies would drift.

**Decision:** the field model moves into shared source files (`src/field/*.glsl.h`).
These compile as C++ (doubles, glm) and as GLSL (floats). glm mirrors GLSL's
names, which makes this possible with a few macros:

| Need | C++ | GLSL |
|---|---|---|
| Scalar and vector types | `real` = `double`, `real3` = `glm::dvec3` | `real` = `float`, `real3` = `vec3` |
| Out-parameters | `INOUT(T)` = `T&` | `INOUT(T)` = `inout T` |
| 64-bit integers (the lattice hash) | `uint64_t` | `uint64_t`, via `GL_EXT_shader_explicit_arithmetic_types_int64` |
| Fixed arrays, structs, `clamp`, `mix`, `floor`, `exp`, `pow` | glm and `<cmath>` | built-ins |

The shared code obeys the intersection of the two languages:
- no lambdas, templates, references other than `INOUT`, or standard containers;
- fixed-size arrays only;
- no recursion.

`EvaluateLocal`'s lambda becomes a function. The CPU march loop
(`RayIntervals`, the vector of intervals, threading) and the GPU's dispatch stay
native to each side. Only the per-point and per-step functions are shared.

The cost: C++ in those files reads like shader code. Every other file stays as
it is.

## 3. Precision and the oracle

The CPU path stays in double and remains the reference. The GPU computes in
float, except the lattice hash, which keeps its 64-bit integer mixing. Changing
the hash would change every sky's noise, and the stylized look was tuned on it.

Float is enough because of where positions are evaluated:
- **Galaxy-local frame.** Each galaxy is evaluated relative to its own centre, as
  today. A galaxy 780 kpc away never puts 780 kpc into a noise coordinate:
  coordinates reach about 15 kpc / 25 pc × 2⁵ ≈ 2 × 10⁴ lattice units, where a
  float resolves 2 × 10⁻³ of a cell.
- **Distance along the ray.** Measured from the start of its interval, not from
  the observer.

The GPU does not reproduce the CPU's bytes. It is judged against the CPU on the
same scene and passes (§6). The tolerances there are the contract.

The field oracle's tolerance is float's measured floor, not 10⁻⁴. The dust
log-normal magnifies the rounding of a point to float about 26-fold: a GPU
exact on its float input still scores 2.9 × 10⁻⁴ on the Milky Way. The arm
phase reaches about 10 rad and needs about 3 × 10⁻⁷, which float cannot hold:
the small spiral measures 1.5 × 10⁻³. The cook oracle judges what that costs
in the image. If the
measured error exceeds them, that is a finding to bring to the owner, not a
reason to loosen the test.

For a given device and driver, GPU output is deterministic: fixed pass order, no
atomics, and each texel accumulated by one invocation.

## 4. The Vulkan side

- **Device.** A headless instance and a compute queue. No surface and no
  window-system extensions. Required:
  - Vulkan 1.2;
  - the `shaderInt64` feature;
  - a compute-capable queue.

  When the device offers `VK_EXT_global_priority`, the queue requests low
  priority, because the machine's GPU is shared with the desktop and with other
  benchmarks.
- **Loading.** The binary does not link `libvulkan`. It loads Vulkan at run time
  through vendored volk (`third_party/volk`, recorded in `VERSIONS`), with
  vendored `Vulkan-Headers`. On a machine without Vulkan, the binary still runs
  and the CPU path is used.
- **Shaders.** GLSL compute shaders, compiled to SPIR-V at build time by `glslc`
  and embedded in the binary as byte arrays. When CMake does not find `glslc`,
  the GPU path is compiled out (`STARSCAPE_GPU=OFF`) with a configure-time
  message. The tests then report the GPU tests as skipped, never as passed.
- **Data.** Uploaded once per cook as storage buffers:
  - the prepared galaxies, as std430 mirrors of the shared structs, capped at 16
    galaxies;
  - the population tables;
  - the flux threshold and march parameters.
- **Dispatch.** Each pass covers all six faces in tiles of rows, sized from the
  first tile's measured time to stay under about 0.25 s per dispatch. That keeps
  the display responsive and the driver's watchdog quiet.
- **Accumulators.** The per-texel sums live on the host. Around each face's
  dispatches, that face's slice is uploaded and read back. At face 2048 a slice
  is 4 M texels × 27 floats ≈ 450 MB. The copy costs well under a second per
  face per pass, against minutes of marching. That makes one path for every face
  size, with no device-memory budget logic.
- **Memory.** The full accumulators take 6 · S_face² · 27 · 4 bytes on the host:
  42 MB at 256, 2.7 GB at 2048. Today's CPU cook already holds the budget's
  share of that. Decoupling the budget's grid from the diffuse face size would
  shrink it. That is a later spec, recorded here because face 2048 makes it
  visible.

## 5. Choosing the device

```
starscape cook <scene.toml> -o <out> [--device auto|gpu|cpu] ...
```

- **`auto` (default):** the GPU when a device meets §4's requirements and the
  scene has at most 16 galaxies; otherwise the CPU, with one log line saying
  why.
- **`gpu`:** the same requirements, but an unmet one is an input error naming
  it.
- **`cpu`:** today's path, progressive.
- The cook's last log line names the device that marched, with its name and
  driver version for the GPU. A file's bytes depend on that device, so the log is
  where a reader finds out which one it was.
- `--threads` still sets the CPU's threads for the calibration, the star draws
  and the previews.

## 6. Testing

Tests marked GPU need a device. They run as their own ctest entry. With no device,
or with `STARSCAPE_GPU=OFF`, that entry prints the reason and exits with ctest's
`SKIP_RETURN_CODE`, so the summary shows it as skipped, never as passed.

| Test | Assertion | Mutation that must fail it |
|---|---|---|
| Pass order covers | For S = 4: the 16 passes visit every stratum exactly once; passes 0–3 hit four distinct quadrants; passes 0–7 hit each quadrant twice | qy = p₁ without the ⊕ p₀ |
| Jitter is today's | For 10³ texels and every stratum: the progressive cook's jitter equals the old nested-loop `RandomStream` sequence, exactly | take stratum k from block 2k |
| Progressive equals batch | CPU, small scene, final quality: the 16-pass result equals a direct mean of the same 16 rays per texel to 10⁻¹² relative | divide the sums by S² instead of n |
| Partial output | A CPU cook stopped after pass 4 (a test hook): the file parses, its diffuse equals the mean of passes 0–3, and its stars come from that budget | write the sum instead of the mean |
| Thread determinism | CPU quick and final cooks with 1 and with 8 threads: byte-identical | seed a draw by thread index |
| Hash and Philox on the GPU (GPU) | A test-only compute entry evaluates `LatticeHash` and `Philox4x32_10` on 10⁵ inputs: equal to the CPU, bit for bit | truncate the hash's mixing to 32 bits in GLSL |
| Field oracle (GPU) | Stylized scene, 10⁵ random points inside each galaxy's bound (including the small spiral 790 kpc away): GPU `GalaxySample` (densities, extinction, gas) within 2 × 10⁻³ relative of the CPU at the 99.9th percentile (owner ruling 2026-10-16: the float floor, below) | evaluate a galaxy in the scene frame instead of its local frame |
| Cook oracle (GPU) | Stylized scene, face 64, final: total diffuse flux within 0.1% of the CPU; per-texel radiance and per-bin budget within 1% at the 99th percentile; drawn star count within 3σ of Poisson | use the step's start instead of its midpoint in the GPU march |
| Device fallback | `--device auto` with no device (a test hook): CPU cook and a log line; `--device gpu` with no device: exit 1 naming the missing requirement | fall through to the CPU on `--device gpu` |
| Galaxy cap | 17 galaxies: `auto` uses the CPU; `gpu` is an input error naming the cap | drop the cap check |

**Timing (not a gate):** the plan reports, from the dev machine's GPU, the
stylized scene's final cook at faces 256, 512 and 1024, beside the CPU's time at
256. These numbers decide whether the resolution test's 2048 cooks are practical.
